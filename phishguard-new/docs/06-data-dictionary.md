# 6. Data and model package

Where the data comes from, how it is licensed, how the corpus is built and
split, what all 265 features are, and what a saved model actually contains.

---

## 6.1 Data sources and provenance

`DATASET_REGISTRY` in `src/phishguard/data/loaders.py` records every corpus the
project cites. Nothing here is downloaded automatically and nothing is
vendored: the loaders read from a directory the operator points them at.

| Key | Name | Format | Licence | Source | Notes |
|---|---|---|---|---|---|
| `synthetic` | PhishGuard synthetic corpus | generated | MIT (generated by this repository) | `src/phishguard/data/synthetic.py` | **Default corpus.** Deterministic given the seed, carries behavioural context, contains no personal data |
| `nazario` | Nazario Phishing Corpus | mbox | Research use; check the maintainer's terms before redistribution | https://monkey.org/~jose/phishing/ | Phishing only — must be paired with a ham corpus. Contains real recipient addresses; treat as personal data and never commit it |
| `enron` | Enron Email Dataset | eml | Public domain (released via FERC investigation) | https://www.cs.cmu.edu/~enron/ | Legitimate mail only, and from 2001 — vocabulary and formatting drift make it a pessimistic ham source for a modern classifier |
| `spamassassin` | SpamAssassin Public Corpus | eml | Apache-2.0 style; see corpus README | https://spamassassin.apache.org/old/publiccorpus/ | Ham + spam. Spam is not the same class as phishing — relabel with care |
| `phishtank` | PhishTank verified phishing URLs | urls | Free for non-commercial use with attribution; API key required | https://phishtank.org/developer_info.php | URL-only. Feeds the URL family; the email family degrades to defaults |
| `uci_phishing_urls` | UCI Phishing Websites / URL datasets | csv | CC BY 4.0 | https://archive.ics.uci.edu/ | Pre-extracted features in some variants; use the raw-URL variant here |

The loaders accept four input shapes — `csv` (one row per message, with column
aliases so most published corpora load without a mapping file), `mbox`, a
directory of `eml` files, and a plain URL list — and map all of them onto
`EmailMessage`, so `phishguard train --data-source <path>` works unchanged.

**Why the synthetic corpus is the primary one.** Three reasons, all recorded in
the generator's module docstring and all defensible under questioning:

1. **Behavioural features do not exist in public corpora.** Enron, Nazario and
   the UCI URL sets are message archives. None of them record whether this
   sender has ever written to this recipient before, what hour the message
   arrived in the recipient's timezone, or how many addresses shared a display
   name last week. A tri-modal system cannot be trained on data missing an
   entire modality, and it certainly cannot be *ablated* on it — the modality
   experiment in [§5.4](05-test-strategy.md) would have nothing to remove.
2. **Privacy and licensing.** Real phishing corpora contain real victims'
   addresses. Committing personal data is forbidden by the project's own
   acceptance criteria, and a generator sidesteps the problem entirely rather
   than managing it.
3. **Reproducibility.** A fixed seed produces identical data on any machine, so
   every number in the evaluation dossier can be regenerated by an examiner in
   one command, with no downloads and no accounts.

The loaders exist so that any claim here can be cross-checked against real
data. When they are used, `BehavioralContext.available` is set to `False`
rather than invented, the feature layer records that as
`beh_context_available = 0`, and the model treats "no context" as its own
regime — see [§6.5](#65-feature-dictionary).

## 6.2 Permissions, consent and licensing

**No personal data is committed to this repository.** The corpora above are the
operator's responsibility to obtain, under whatever terms their individual
licences impose. Nothing in this repository fetches them.

`.gitignore` enforces the mechanical half of that promise:

```
data/          artifacts/     *.mbox     *.eml
*.db  *.db-wal  *.db-shm      *.joblib   *.pkl   *.onnx
.env  .env.*    *.pem  *.key  secrets/   api_keys.txt
```

The `security` CI job is the other half: it fails the build if a value that
looks like an API key or a pseudonymisation salt is committed to a `.py`,
`.yml`, `.yaml` or `.env` file (see [§5.6](05-test-strategy.md)).

**The synthetic corpus carries no personal data.** It is MIT-licensed, being
generated by this repository. Every organisational domain it invents uses the
`.example` TLD reserved by RFC 2606 for exactly this purpose — the internal
domain is `northgate-industries.example`, partners are
`meridian-supplies.example` and similar. Names are drawn from a pool of
generic first and last names combined at random. Recipient addresses are random
six-character slugs at the internal domain. Real brand names and their real
domains (`paypal.com`, `microsoft.com`, `hdfcbank.com`) do appear, because
brand impersonation is the phenomenon being modelled and a lookalike-distance
feature needs something to be a lookalike *of*; they identify organisations,
not people.

**Runtime data minimisation** is a separate concern with its own controls: the
audit trail stores a pseudonymised sender, a sender domain and a subject hash,
never message content, and the logs carry the same projection. Both are
asserted by tests ([§5.3](05-test-strategy.md)) and specified in
[§3](03-api-contract.md).

## 6.3 The synthetic corpus

`src/phishguard/data/synthetic.py` is a seeded generator, not a template
filler. The design is worth explaining in detail, because the credibility of
every downstream number rests on the corpus being a real task rather than a
solved one.

### Campaign structure

Mail traffic is *campaign-structured*, and the generator models that directly.

A **campaign** fixes an identity — lure type, brand, sending domain, landing
page host and path, greeting, sign-off, authentication outcome, URL style —
and then emits between 1 and 40 messages that differ only in per-victim tokens:
the reference number, the amount, the deadline in hours, the device and city in
the "unusual sign-in" pretext, the tracking token in the URL. This is exactly
what a real phishing kit does, and it is why near-duplicate messages exist in
real inboxes.

Campaign size is drawn from a distribution that depends on the campaign class,
because a targeted BEC attempt is one message and a bulk mailing is dozens:

| Size class | Sizes (weighted) |
|---|---|
| `phish_bulk` | 1, 2, 4, 8, 16, 32 |
| `phish_targeted` | 1, 1, 2, 3 |
| `ham_personal` | 1, 1, 1, 2 |
| `ham_bulk` | 3, 6, 12, 25, 40 |
| `ham_mixed` | 1, 2, 4, 8, 16 |

Every message carries a `group_key` naming its campaign
(`phish-bank-00042`, `hamhard-real_invoice-00117`), which is what lets
`phishguard.data.splits` keep whole campaigns on one side of a split. On the
9 000-message corpus of the committed dossier this produces 1 256 campaigns.
Each campaign also occupies a short window rather than the whole corpus span,
so the temporal split has something meaningful to cut.

### Compositional bodies

Bodies are composed slot by slot from the sentence banks in
`src/phishguard/data/banks.py` — a greeting, a pretext drawn from the pool for
that lure type, an evidence line, a pressure line, a call to action, a
consequence, a sign-off, a footer — rather than emitted from a fixed template
per lure. Two different campaigns of the same lure type — two `bank` campaigns,
say — are therefore genuinely different text, not the same paragraph with a
different brand name substituted. Legitimate mail is built the same way, from
opener, body, detail, closer and optional long-tail banks.

### Difficulty by design

The generator is parameterised at `phish_ratio = 0.42`,
`hard_ham_ratio = 0.34` and `hard_phish_ratio = 0.40`. "Hard" means the class
is not decidable from vocabulary.

**Hard legitimate mail (~34%)** is drawn from two pools. `HARD_HAM_BODIES`
supplies genuine password resets, genuine security alerts, genuine MFA codes,
genuine invoices with a PDF attached, genuine shipping notices and genuine
payroll notifications — messages that trip every phishing lexicon while being
entirely real. About 38% of the hard-ham branch instead produces
`suspicious_ham`: legitimate marketing, onboarding and billing mail that uses
shorteners, deadlines, freshly stood-up campaign subdomains and "confirm your
email" calls to action. These are the false positives that get a filter
switched off in production, so they belong in the training distribution rather
than being discovered after deployment.

**Hard phishing (~40%)** is business email compromise (a short, fluent,
lexically unremarkable request from a squatted internal domain with a freemail
`Reply-To`), thread hijacking (`Re: Re: <topic>` with a quoted prior message
and a single new link), vendor swap (a change-of-bank-details letter with a PDF
attachment and no link at all), plus recruiter, document-share and
calendar lures. Separately, and drawn independently of the hard/easy split, 20%
of all phishing campaigns are **clones**: the message text is the brand's own
genuine transactional template, taken verbatim from `HARD_HAM_BODIES`, with
exactly two things changed — the link destination and the sending domain. On a
clone the body carries no discriminating signal whatsoever, which is precisely
why a text-only classifier cannot solve phishing detection. The dossier reports
the hard slice separately: macro F1 0.95475 across 489 test messages, against
0.98805 overall, and the slice holds all 22 of the test set's missed phishing
messages.

### Overlapping distributions

Difficulty is not enough on its own. If any single generated attribute lined up
with the label, the corpus would be a lookup table wearing a classifier's
clothes. The generator therefore overlaps the class-conditional distributions
deliberately:

| Attribute | How it overlaps |
|---|---|
| SMTP authentication | `HAM_AUTH` and `PHISH_AUTH` are weighted tables that intersect heavily. 62% of legitimate mail passes SPF+DKIM+DMARC, but the rest fails in realistic ways — forwarding breaks SPF (`softfail`), mailing lists rewrite and break DKIM, many partner domains publish no DMARC record. 30% of *phishing* passes all three, because the attacker owns the throwaway domain and publishes correct records for it |
| Sending domains | Both classes draw from a long tail of unremarkable business domains generated by `_business_domain` — `northfield-logistics.co.uk`, `cedarworks42.net` — across seventeen TLDs. 35% of attacker infrastructure has no keyword, no odd TLD and nothing to flag, including aged domains bought precisely to defeat age heuristics |
| HTTPS | 92% of phishing links and 99% of legitimate links use HTTPS. Free certificates are universal; the modern web does not separate on scheme |
| URL paths | One shared vocabulary (`SHARED_URL_PATHS`) for both classes. `/signin`, `/account/verify`, `/billing/payment` are where the genuine pages live, and a phishing kit is a copy of the genuine site |
| Redirect wrappers | ESP click-tracking wrappers appear on 33% of genuine bulk links and 15% of phishing links. Structurally they are identical to an open-redirect evasion: a neutral host, an opaque token and the real destination nested inside |
| Sender/brand alignment | About a quarter of genuine brand mail leaves from an ESP or a subsidiary domain (`mail-relay-svc.net`, `microsoft-notify.com`), so a display-name/domain mismatch is strong evidence rather than proof |
| Footer links | Phishing kits copy the brand's genuine footer links along with the template, so most links in a phishing email point at the real brand and only one is hostile — which is why "any bad link" and "ratio of good links" are both weak tests on their own |
| Behavioural context | Label-conditional but heavily overlapping. A legitimate newsletter is also first-seen and also arrives in a burst; a thread-hijack phish sits inside a real conversation; a marketing campaign runs from a two-week-old subdomain |

### Artefacts caught during development

The leakage audit ([§6.4](#64-splitting-strategy)) is not decoration. Four
generator artefacts were caught by it during development, each of which would
have inflated the headline numbers into meaninglessness. They are documented
here because a corpus generator that has never been caught lying is one that
has not been checked.

| # | What the audit reported | Cause | Fix |
|---|---|---|---|
| 1 | `hdr_auth_score` separating the classes at **AUC 0.997** | Every legitimate message was given a clean SPF/DKIM/DMARC pass and every phishing message a failure | Replaced with the overlapping `HAM_AUTH` / `PHISH_AUTH` weighted tables: legitimate mail fails through forwarding and list rewriting, phishing passes on attacker-owned domains |
| 2 | `body_length` at **AUC 0.96** | Phishing was systematically longer: every phishing body carried a full pretext plus a footer, while every generated ham was a three-line note | Legitimate mail gained a long-tail paragraph — `HAM_LONG_TAIL` via `_maybe_tail`, applied to 25–45% of bodies depending on kind — so that the two length distributions overlap, because real business email is not uniformly terse |
| 3 | `url_lookalike_distance` at **AUC 0.97** | Distance-like features were zero-filled for messages with no links, making "no links at all" indistinguishable from "links pointing at the brand's genuine domain" — the opposite meaning | Neutral defaults (`_DISTANCE_LIKE`, value 9.0) for `url_lookalike_distance__max`, `url_lookalike_distance__mean` and `link_min_lookalike_distance` when a message has no links |
| 4 | The word model learned `http` as its single strongest phishing token | 45% of phishing links were plain HTTP while legitimate links were all HTTPS | Realistic rates: `HTTPS_RATE_PHISH = 0.92`, `HTTPS_RATE_HAM = 0.99` |

A fifth was caught by inspection rather than by the audit: making
display-name/domain mismatch a deterministic phishing signal let the header
block *alone* reach 0.996 macro F1. The fix was `ESP_SENDING_DOMAINS` — brands
use email service providers, resellers and subsidiary domains constantly, so
the mismatch is evidence, not proof.

`test_no_single_feature_dominates_the_corpus` now asserts that no feature among
the 265 exceeds 0.985 single-feature AUC, and the audit runs on every training
and evaluation run. On the committed dossier it reports zero suspicious
features, zero exact duplicates, zero near-duplicates and zero group overlap.

## 6.4 Splitting strategy

`src/phishguard/data/splits.py` makes the standard failure mode impossible by
construction and then proves it with an audit.

**Why a random row-level split is invalid here.** One kit generates hundreds of
near-identical messages. A random split over rows therefore places siblings of
a test message into training: the model memorises the campaign, scores near
perfectly on the held-out half of the same campaign, and collapses the first
time it meets a campaign it has not seen. The reported accuracy is a
measurement of memorisation, not of generalisation, and nothing downstream of
it means anything.

**Three guarantees:**

1. **Group disjointness.** Splits are made over `group_key` — campaign or
   thread — never over rows, so no campaign spans two splits. Groups are
   bucketed by majority label first and each class's test quota is filled
   greedily *by message count* rather than by group count, because campaign
   sizes vary by more than an order of magnitude and taking 25% of the groups
   would drift the class balance by several points. A group that would
   overshoot its quota by more than half its own size is skipped rather than
   dragging the balance with it.
2. **Near-duplicate separation.** Every message is shingled into overlapping
   5-character strings and reduced to a 64-permutation MinHash signature.
   Candidate pairs are found by LSH banding (16 bands of 4 rows), which keeps
   the comparison near-linear — an exact 12 000 × 12 000 comparison would
   dominate a training run. Any test message whose estimated Jaccard similarity
   to a training message reaches **0.85** is dropped from the test set and
   counted in `dropped_near_duplicates`.
3. **Feature-label sanity.** Every feature is scored for single-feature AUC on
   the training half via the rank-sum identity, with ties averaged so a
   constant feature scores exactly 0.5. Anything at or above **0.985** is
   reported as suspicious. This is how the artefacts in §6.3 were found.

`audit_leakage` combines all of it into one pass/fail report: exact duplicate
pairs (by message fingerprint), near-duplicate pairs, group overlap, train and
test sizes, phishing rates on both sides, the suspicious-feature list, and a
class-balance check that fails if the phishing rate drifts by more than 0.08
between splits. `phishguard train` refuses to train when the audit fails
(exit code 2) unless `--allow-leakage` is passed explicitly, and gate G10 makes
a failed audit a build failure.

On the committed dossier the audit reports: 6 750 train / 1 938 test, 1 256
campaign groups of which 284 are in the test set, zero exact duplicates, zero
near-duplicates, zero group overlap, zero suspicious features. The class
balance drifts from 0.4329 to 0.4644 — a delta of 0.0315, well inside the 0.08
tolerance but not free. Grouped splitting on campaign-structured data costs
some balance precision; that is the trade being made, and it is reported rather
than tuned away.

**The temporal split.** `temporal_split` sorts by `received_at`, trains on the
first 75% and tests on the remainder, then removes from the test set any
campaign that straddles the cut, and finally applies the same near-duplicate
scrub. It is the harsher and more operationally honest question — *does a model
fitted on January hold up in June* rather than *can it interpolate within a
shuffled pool* — and on this kind of data it typically costs 3–8 F1 points,
because campaign vocabulary drifts. Both strategies are available from the CLI
and the dossier records which one produced each result.

## 6.5 Feature dictionary

265 features in three families, in a fixed order derived once, frozen into the
saved artefact and verified on load. The order is the concatenation of the
family name tuples in the order `email`, `url`, `behavioral`; dropping a family
(the modality ablation) drops a contiguous block.

| Family | Features | Module |
|---|---|---|
| Email | 125 | `features/email.py` |
| URL | 107 | `features/urls.py` |
| Behavioural | 33 | `features/behavioral.py` |
| **Total** | **265** | `features/assembler.py` |

All text signals are computed on the **canonicalized** string (defence
`D-NORM`), while the obfuscation deltas between raw and canonical text are
themselves retained as features — so an attacker cannot obtain a cleaner
feature vector merely by making the message harder to read.

### Email family — 125 features

| Group | Count | Representative names | What it measures |
|---|---|---|---|
| Header identity | 35 | `hdr_display_brand_domain_mismatch`, `hdr_replyto_domain_mismatch`, `hdr_returnpath_domain_mismatch`, `hdr_lookalike_distance`, `hdr_sender_freemail`, `hdr_sender_disposable`, `hdr_sender_high_risk_tld`, `hdr_sender_domain_entropy`, `hdr_local_entropy`, `hdr_spf_fail`, `hdr_dkim_fail`, `hdr_dmarc_fail`, `hdr_auth_score`, `hdr_received_hops` | Who the message claims to be from and whether the envelope, the display name and the authentication results agree |

**The nine obfuscation-delta features**, listed in full because they are
conceptually the most important block in the family:

| Feature | Measures |
|---|---|
| `obf_zero_width_count` | Zero-width and joiner characters removed |
| `obf_bidi_count` | Bidirectional-override characters removed |
| `obf_confusable_ratio` | Share of characters folded from a confusable script |
| `obf_diacritic_ratio` | Share of characters that carried a stripped combining mark |
| `obf_nonascii_ratio` | Non-ASCII density of the raw text |
| `obf_separated_tokens` | Tokens rejoined from `p-a-s-s-w-o-r-d` style separation |
| `obf_leet_tokens` | Tokens un-leeted (`p4ssw0rd` → `password`) |
| `obf_norm_edit_ratio` | Relative length change between the raw and canonical strings — how much canonicalization had to remove |
| `obf_mixed_script_words` | Words mixing two scripts, e.g. Cyrillic `а` inside `paypal` |

Canonicalization does not discard what it undid. An attacker who obfuscates
heavily to defeat the character- and word-level text members pays for it in the
engineered member, because the effort itself is nine numbers on the feature
vector. **Evasion effort is evidence.**

Message-level roll-ups (25):

| Group | Representative names | What it measures |
|---|---|---|
| Volume and spread | `link_count`, `link_unique_domains`, `link_domain_diversity`, `link_https_ratio` | How many destinations the message has and how consistent they are |
| Any-link flags | `link_any_ip_host`, `link_any_shortener`, `link_any_punycode`, `link_any_redirect_param`, `link_any_at_symbol`, `link_any_brand_mismatch`, `link_any_brand_lookalike`, `link_any_brand_squat`, `link_any_brand_impersonation`, `link_any_free_hosting` | The single worst property present anywhere in the message |

`max` captures *the single worst link*, which is what decides the outcome.
`mean` captures *how consistently bad the message is*, which separates a
hijacked newsletter from a purpose-built lure. Three features are given a
neutral default of 9.0 rather than 0.0 when a message has no links at all —
see artefact 3 in [§6.3](#artefacts-caught-during-development).

### Behavioural family — 33 features

| Group | Count | Names | What it measures |
|---|---|---|---|
| Relationship | 9 | `beh_context_available`, `beh_sender_first_seen`, `beh_prior_messages`, `beh_prior_messages_log`, `beh_prior_replies`, `beh_reply_ratio`, `beh_relationship_strength`, `beh_thread_depth`, `beh_is_new_thread` | Two-way correspondence history. `beh_relationship_strength` saturates: one prior message is weak evidence, forty with replies is strong |
| Timing | 3 | `beh_hour_local`, `beh_off_hours`, `beh_is_weekend` | Arrival time in the recipient's local frame; off-hours is outside 07:00–21:00 |
| Distribution | 5 | `beh_recipient_count`, `beh_bcc_count`, `beh_bcc_ratio`, `beh_mass_mailing`, `beh_external_sender` | The shape of the recipient list |
| Reputation and age | 6 | `beh_domain_report_count`, `beh_domain_reported`, `beh_domain_click_rate`, `beh_domain_age_days`, `beh_domain_age_log`, `beh_young_domain` | Prior user reports, historic click rate, and domain age (young is under 90 days) |
| Campaign shape | 5 | `beh_burst_count_1h`, `beh_burst_log`, `beh_campaign_shape`, `beh_display_name_alias_count`, `beh_display_name_reuse` | Volume from one domain in an hour, and one display name appearing behind several addresses |
| Interactions | 5 | `beh_cold_contact_with_ask`, `beh_odd_hour_and_urgent`, `beh_external_and_financial`, `beh_young_domain_and_ask`, `beh_trust_deficit` | Cross-family products an attacker cannot rewrite away by editing text alone |

`beh_trust_deficit` is a single 0–1 scalar an analyst can read: a weighted
combination of first-contact, young domain, off-hours arrival, the inverse of
relationship strength, and the size of the ask. High means a stranger on new
infrastructure is asking for something at an odd hour.

**Absence is a value, not a zero.** When the gateway supplies no sender history,
`beh_context_available` is 0 and the rest of the block sits at defined neutral
defaults rather than at misleading zeros. The model learns "no context" as its
own regime, and the verdict says so in the evidence list.

### The feature contract

`FeatureAssembler.contract()` serialises the families, the
`canonicalize_urls` flag, the feature count, the full ordered name list and the
per-family sizes. `verify()` compares a loaded contract against the runtime
assembler and raises `RuntimeError` on any difference, naming the first missing
and first unexpected features. Drift between training-time and serving-time
features is the most common cause of a model that scores well offline and fails
silently in production — the vector still has the right shape and the numbers
still look plausible — so it is a hard failure at load time rather than a
warning.

`src/phishguard/models/registry.py` persists the whole decision system, not an
estimator.

```
artifacts/models/
    pg-0e0dffa24f/
        detector.joblib      members, fusion weights, calibrator, defence config
        manifest.json        version, contract, metrics, provenance
    current                  pointer file naming the active version
```

`save_detector` refuses to write an untrained detector. `current_version` reads
the pointer file, verifies the named version actually exists on disk, and falls
back to the most recently modified version directory if the pointer is missing
or stale. `promote(version)` rewrites the pointer; `prune(keep=5)` deletes all
but the newest five versions and never the current one.

The manifest carries:

| Field | Contents |
|---|---|
| `version`, `created_at`, `trained_at` | Identity and timestamps |
| `environment` | `phishguard`, `python`, `platform`, `numpy` and `scikit_learn` versions |
| `members` | The fitted members — `rules`, `engineered`, `charngram`, `wordtfidf`, optionally `transformer` |
| `feature_families` | Which of `email`, `url`, `behavioral` are active |
| `defenses`, `active_defense_ids` | Which controls were on during training (`D-NORM`, `D-URL`, `D-ADVTRAIN`, `D-ENSEMBLE`, `D-ABSTAIN`, `D-VELOCITY`) |
| `thresholds` | The review and block band edges at save time |
| `calibration_method` | The method the calibrator actually fitted — `isotonic`, `platt` or `none` |
| `training` | The full training report: pool sizes (`n_fit`, `n_stack`, `n_cal`), adversarially augmented count, fusion weights and intercept, calibration before/after ECE and Brier, training seconds, and the **feature contract** |
| `metrics` | Held-out scores at save time |
| `provenance` | Corpus description, split strategy and notes, leakage-audit outcome, train and test sizes |

The committed model, `pg-0e0dffa24f`, records 4 025 fit / 1 492 stack / 1 233
calibration messages, 1 747 adversarially augmented phishing messages, fusion
weights of `rules` 2.22, `engineered` 4.06, `charngram` 5.04, `wordtfidf` 4.37
against an intercept of −6.71, isotonic calibration, and a 265-feature contract
split 125 / 107 / 33.

**The contract is verified at load.** `load_detector` reads
`manifest["training"]["feature_contract"]` and calls
`assembler.verify()` on the engineered member. A mismatch raises rather than
warns. Runtime settings then override the training-time copy, so band
thresholds can be retuned operationally without retraining — the one thing that
is deliberately *not* frozen into the artefact.

Provenance in the manifest is what makes a result reproducible six months
later: the corpus seed and size, the split strategy, the library versions and
the defence set are all recorded. `phishguard train` writes it and the model
card reads it.

## 6.7 Reproducibility

Everything in the evaluation dossier is regenerable from three commands, on any
machine, with no network access:

```bash
phishguard data     --n 12000 --show-kinds   # build the corpus and audit it
phishguard train    --n 12000 --save         # train and register a model
phishguard evaluate                          # dossier + acceptance gates
```

Or, through the Makefile, `make all` (train, evaluate, model card, OpenAPI) and
`make ablation` for the slower run that includes the defence ablation.

**The seed is fixed at 20260907.** `generate_corpus` takes it as a default and
`--seed` exposes it on every data-taking command. The same seed produces
identical data on any machine: the generator draws from a single
`random.Random` instance and nothing else, so message content, campaign
boundaries, authentication outcomes, behavioural context and timestamps are all
deterministic. `grouped_split` seeds its own shuffle, MinHash uses a fixed
permutation seed, and the attacker takes its seed from settings. CI
additionally pins `PYTHONHASHSEED=0`.

**Nothing is downloaded.** The generator has no network dependency, the feature
extractors never resolve a URL (asserted by test, §5.4), and the public-suffix
and brand lists are curated constants in the source rather than a fetched
snapshot.

The committed dossier in `artifacts/reports/` was produced from a
9 000-message corpus with attack budget 10 over 150 attacked messages,
including the defence ablation (whose arms are attacked on the first 120 of
those messages). The CI acceptance job runs the same pipeline with the same
corpus size, budget and attacked count, but without the defence ablation; the
exact commands are in [§7.1](07-evaluation-dossier.md). Corpus size, attack
budget and the number of attacked messages all move the robustness figures, so
every report records the parameters it was produced with — the corpus as
`synthetic(n=9000, seed=20260907)` under `dataset.split`, the budget and
attacked count in the `robustness` block — and a content fingerprint of the
exact training and test sets under `dataset.train_version` and
`dataset.test_version`: a SHA-256 over the messages and labels, and a
12-character version taken from it. On the committed dossier these are
`a1c09c445b31` for the 6 750 training messages and `f67d182863fb` for the
1 938 test messages. The same sets give the same versions on any machine, and
one changed message or label changes them. A run at a different `--n` will not
reproduce these numbers exactly, and is not meant to.
